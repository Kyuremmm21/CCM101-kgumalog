# Mission Reflection

Checking the host server’s resources remains critical even when containers appear to be running perfectly. Containers share the underlying host’s CPU, memory, and disk. If the host itself is running low on resources, every container on that machine will eventually suffer from performance degradation or failure. Establishing a baseline helps detect potential bottlenecks before they affect the applications.

When a user reports that they cannot log into a web application, the `docker logs` command becomes a powerful diagnostic tool. By examining the application logs, an engineer can see the exact HTTP requests the user made, the status codes returned, and any error messages generated by the application. This information quickly reveals whether the problem is a 404 (wrong URL), a 401/403 (authentication issue), or a 500 (internal server error).

There is a clear difference between monitoring logs and monitoring metrics. Logs provide detailed, event-level information about what happened inside the application—individual requests, errors, and messages. Metrics, on the other hand, show quantitative data such as CPU percentage, memory consumption, and network I/O over time. Logs answer “what happened,” while metrics answer “how much” and “how healthy” the system currently is.

Large enterprise companies monitor thousands of containers using centralized observability platforms such as Prometheus for collecting metrics and Grafana for visualizing them. These tools automatically scrape metrics from every container and host, store them in a time-series database, and allow engineers to create dashboards and alerts. When a threshold is breached, the system can notify the on-call team immediately.

Through this laboratory activity, my ability to troubleshoot Linux environments has significantly improved. I am now more comfortable using native commands such as `free`, `df`, and `top`, as well as Docker-specific tools like `docker logs` and `docker stats`. I have learned to combine host-level checks with container-level observability, giving me a more complete picture of system health. This experience has strengthened my confidence in diagnosing performance and availability issues in cloud environments.
